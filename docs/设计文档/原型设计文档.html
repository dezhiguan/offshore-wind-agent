一、设计目标与使用角色

系统回答的是风机运行与检修合规问题，结论会影响现场作业决策。界面的第一目标不是"答得好看"， 而是让人能判断这个结论该不该采信。三条设计主张贯穿全部页面：

  1. 结论与依据同屏可达：任何一句结论，都能在同一页内展开到它所依据的 SQL、命中行或条款原文。
  2. 边界前置：系统答不了什么，在用户提问之前就写在页面上，而不是问完才说"无法确认"。
  3. 口径随指标出现：凡是给出数字的地方，同屏标注它的统计口径与样本量；不给没有口径的分数。
角色主要诉求入口
现场与值班人员问清楚某台风机的状态、告警、工单安排与作业是否合规，并知道还要现场核实什么问答页 /
技术复核人员逐段复核 Agent 的决策过程：调了哪些工具、取回了什么、护栏是否触发后台 → 链路追踪
质量与运维负责人看回归用例是否全过、线上真实流量是否被接住、代价与上下文水位后台 → Agent 质量中心

信息架构

 ┌ 问答页 /  ────────────────────────────────────────────── 面向使用者
 │   能力说明（可以回答 / 无法回答）
 │   提问框 + 示例问句
 │   执行时间线（流式）→ 回答 → 核实清单 → 未完成 / 待核实 → 数据源 → 依据

 └ 管理后台 /admin ───────────────────────────────────────── 面向复核与运维

     │    ├ 离线评测   固定用例 + 断言，判得出对错

页面边界是刻意的。链路追踪页不出任何聚合指标：同一个"工具调用成功率"， 在链路页（最近 50 条、线上与回归混算、重启归零）与质量中心（固定用例集 / 真实流量分档） 必然给出不同数值，两处并存只会让人以为系统在自相矛盾。聚合口径统一归质量中心， 链路页只负责"从一堆链路里挑出该点开的那一条"。

三、全局设计规范

3.1 版式

项问答页后台
栅格单列，内容区最大宽 880px，居中左栏导航 200px + 内容区自适应；链路追踪为列表 / 详情双栏
正文字号15px / 行高 1.7513.5px / 行高 1.7（信息密度优先）
卡片1px 描边 + 8px 圆角，不使用投影同左；指标块统一为「标题 + 口径副标题 + 指标网格」
折叠原始依据默认折叠（<details>）span 输入输出参数默认折叠

3.2 状态色语义

全站只有一套状态语义，问答页的核实清单与后台的 span 状态共用同一组含义：

语义标记问答页含义后台含义
已确认 / OK实心 ✓资料明确支持该项该段按预期完成
明确不满足 / ERROR实心 ✕资料明确不支持（如备件不可用）该段失败（模型超时、工具报错）
待现场核实 / DEGRADED空心资料没有记录，需现场确认并留痕按预期收紧：预算拦截、未取证打回
"明确不满足"与"待现场核实"永远分开显示。前者是已知的坏消息， 后者是系统的边界。合并成一类，用户就分不清哪些已成定论、哪些还要去查——在电力安全场景里 这不是措辞问题。

3.3 文案规范

  • 不用绝对化表述替代判定结论；结论句必须能追到依据区的某一条证据。
  • "本轮未查完"与"待现场核实"分属两张卡：前者重跑一次即可消除，后者派人上岛也未必消得掉。 混在一起，读者会把残缺结论当成完整结论。
  • 指标一律"值 + 口径 + 样本量"三件套同屏，例如「P95 28.2s · P50 11.0s · 样本 53」。
  • 涨跌单位分两类且不混用：比率类用百分点 pp，量纲类（耗时、Token、成本）用相对百分比 %； 颜色按好坏给而非按方向给（耗时涨是红、准确率涨是绿）；幅度小于 0.05pp / 0.5% 显示「持平」。

4.2 分区契约

每个区块由回答契约中的一个字段驱动，字段为空时该区块整体不渲染——不出现空卡片。

#区块驱动字段渲染规则
①能力说明静态常驻页首，两列对照；右列末尾固定声明"无记录即标注需现场核实，不推测"
②示例问句静态点击填入输入框，不自动提交，保留用户改写机会
③提问区—最长 500 字；提交中禁用按钮；下方常驻闭区间与数据覆盖范围说明
④执行时间线SSE step / thinking每完成一次工具调用追加一行，显示已用时；被护栏拒绝的调用标注为"已拒绝"并给出原因
⑤回答answer见到 ## 结论 标题才开始渲染（决策轮的自然语言不推送）；支持 answer_reset 撤销
⑥现场核实清单checklists[]仅当本次实际调用过对应规则时生成；三态计数置顶；有 pending 项时显示底部声明
⑦本轮未完成查询truncation / incomplete[]合成一张卡：机器事实（已执行几步、哪类资料整轮未读）+ 模型自陈的该判未判项
⑧其他需现场核实unverifiable[]清单未覆盖的自由文本边界项
⑨使用的数据源sources[]由代码从真实工具调用反推，含规则引擎旁路命中的条款来源
⑩结论依据basis[]由代码从证据渲染，不由模型复述
⑪原始依据evidence.{tables,rules,docs}默认折叠；展开见原始 SQL、命中行表格、规则判定事实、章节全文
⑫查询过程trace[]完成态的完整轨迹，与④的流式行合并为最终形态

失败类型触发页面表现
证据不足拒答两次未调用任何工具正文明确写明"本系统要求所有结论必须有随题资料支撑"，不是白屏；后台计入"未取证拒答率"，不计入任务完成
检索为空召回无命中如实说明资料中没有该条目，不得套用相近条目
SQL 出错语句被守卫拒绝或执行报错错误回灌模型重写一次；仍失败则在时间线上标红该步
模型超时 / 网关异常llm_error给出明确提示而非白屏；该次失败链路仍进留存，使后台成功率有分母
离线回放未匹配replay_miss提示改用示例问题或关闭回放模式

回放模式下页首固定出现一条提示：标明当前为离线回放、匹配到的用例编号与原问题。

5.2 两档口径（页面必须显性说明）

离线评测线上质量
样本eval/ 下的固定用例（回归 / 探针 / 施压 / 边界）用户在问答页真实提出的问题
有无标准答案有断言，判得出对错没有，判不了对错
结论指标结果准确率服务达成（正常收口占比）
数据来源eval/run.py 的落盘产物（只读渲染）进程内链路留存（source=online）
两档的分母互不相交：后台点「运行全部」跑出来的链路标为 source=eval， 一条都不进线上质量。挑好的用例混进线上指标会把成功率抬着走， 而线上质量要回答的恰恰是"真实用户问出来的东西，系统接得住吗"。 页面也不把两档合成"综合质量分"——分数变动时没人说得清是用例挂了还是线上降级了。

5.3 线上质量的指标块

这一档一个"准确率"都不出现，出现的全是系统自己留下的痕迹：

指标块内容口径
服务达成正常收口占比；降级与失败分开数降级 = 给了回答但没走主路径；失败 = 没有回答
回答可用性有效回答率、未取证拒答率、标注存疑占比拒答是护栏生效，不是故障，单列不并入失败
执行健康工具调用成功率、模型调用成功率、链路完成率模型成功率的分母包含失败调用，否则恒为 100%，等于装饰
代价P95 / P50 耗时、平均 Token、单次与累计成本缓存命中的输入按缓存单价折算
上下文红线真实提问压出来的数据行 / 文档字符峰值水位去重口径，与离线档同一套阈值
最近问答分页表，点任意一行跳到链路追踪对应那条进程内最近 50 条，重启即清空，页面写明样本量与时间窗

七、组件规格

7.1 现场核实清单卡

元素规格
标题清单名 + 条款号 + 主体（如「更换前置条件 · 第 5.1 条 · T08」）
计数条「n 项已确认 / n 项明确不满足 / n 项待现场核实 / 共 n 项」，后两项为 0 时不显示
条目三态标记 + 条目名 + 依据注记（如 part_available = 0）
底部声明仅当存在 pending 项时出现：系统只读、不能代为确认、不据此推定其已满足（第 5.2 条）
生成条件本次实际调用过对应规则才生成，不凭空构造

7.2 指标卡

固定三行结构：指标名 + 口径徽标 / 数值 / 注脚（样本量、构成、与上一轮涨跌）。 口径徽标取自实现中的固定词表：ASSERTION、ANSWERED、BY CALL、 NO CUTOFF、NON-EMPTY、REFUSED、FLAGGED。 上一轮与本轮用例数不同时不做对比，页面直接说明用例集有变动。

7.3 证据折叠项

类型摘要行展开内容
数据表数据表 · 查询 n · 命中 m 行原始 SQL（等宽）+ 命中行表格（横向可滚动）
规程判定规程判定 · 规则名 · 第 x.x 条判定结论、逐项事实、引用条款原文
章节原文章节 · 标题该节全文

八、关键交互时序

用户          问答页             /ask/stream            编排层          界面反馈
 │ 输入问题      │                     │                   │
 ├─提交─────────►│                     │                   │

 │              │                     ├─thinking─────────►│ "正在判断需要查询哪些资料…"
 │              │                     ├─step（工具1）────►│ 时间线 +1 行，计时开始
 │              │                     ├─step（工具2）────►│ 时间线 +1 行
 │              │                     ├─token…───────────►│ 答案逐字浮现
 │              │                     ├─answer_reset*────►│ 撤销正文（同轮又调工具）
 │              │                     ├─composing────────►│ "正在整理结论与依据…"
 │              │                     └─done─────────────►│ 完成态：回答/清单/依据/轨迹
 │◄─可展开任一条依据核对────────────────────────────────────┤

为什么要有 answer_reset：决策轮也会输出自然语言（"我需要先查询告警记录"）。 若把所有内容增量都当答案推送，界面会出现"冒出几个字又被下一次工具调用冲掉"的反复闪烁。 因此以三段标题为界，见到 ## 结论 才认定进入最终答案；同一轮里既出现标题又发起工具调用时， 发 answer_reset 撤销已渲染内容；模型完全未按格式输出时，在该轮结束一次性补发。

九、可访问性、响应式与打印

  • 键盘可达：提问框 Enter 提交、Shift+Enter 换行；折叠项与筛选 chip 均为原生可聚焦元素，统一 :focus-visible 描边。
  • 状态不只靠颜色：三态同时有符号（✓ / ✕ / 空心）与文字标签，色觉障碍下仍可分辨。
  • 动效遵循 prefers-reduced-motion：开启后关闭光标闪烁与进度过渡。
  • 响应式：问答页单列自适应；后台在窄屏下左栏收起为顶部横向导航，链路详情由双栏降级为上下堆叠。
  • 宽内容（命中行表格、SQL、span 参数）在各自容器内横向滚动，页面主体不产生横向滚动条。
  • 页面响应头 Cache-Control: no-store，避免改版后取到旧界面。

十一、本期未纳入的原型项

  1. 多轮追问与上下文澄清（当前为单轮问答，界面不保留会话线）。
  2. 登录、角色与权限视图：当前形态为单机单用户，后台无鉴权入口。
  3. 链路与线上质量的持久化视图（当前为进程内最近 50 条，重启即清空，页面已写明）。
  4. 移动端专用版式：现有响应式可用，但未做触屏专项交互。

十二、页面级验收要点

详细判据见《验收标准文档》，此处列页面侧必查项：

  1. 回答区的任一结论，均可在同页展开到其依据（SQL / 条款原文 / 规则判定事实）。
  2. 核实清单的三态不得合并显示；存在 pending 项时底部声明必须出现。
  3. "本轮未完成查询"与"需现场核实"分属两张卡，文案不得互串。
  4. 后台每一处数字均有口径标注与样本量；离线与线上不得出现在同一张表内。
  5. 链路追踪页不得出现任何聚合指标；顶部导航条的筛选可点、可取消。
  6. 四类失败与回放未匹配各有独立文案，均不出现白屏。
