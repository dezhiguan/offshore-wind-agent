一、范围、约束与质量目标

1.1 业务范围

对四类资料做路由、检索与多步取证，融合成带依据的回答，并显式区分 资料支持的事实与现有资料无法确认的事项：

资料介质结构特征典型问题
运行告警记录SQLite 表 alarm_records结构化，按风机 / 故障码 / 时间筛选与计数型号、最近状态、时段告警
维检工单记录SQLite 表 maintenance_records结构化，含自由文本 resolution_note优先级、备件、观察时长
故障处理手册Markdown，按故障代码分节（9 节）每节四个固定子标题触发条件、常见原因、处理步骤
检修作业与安全管理规程Markdown，按「第 x.x 条」分条（25 条）条款即最小判定单位重复故障、禁止复位、关单与换件合规

1.2 强约束

  1. 不得将整个数据库或文档放入模型上下文——这是硬红线，由运行时预算机制拦截，不靠事后统计。
  2. 结论必须可追溯：展示所依据的数据表、文档或章节，且展示内容必须来自真实发生过的工具调用。
  3. 资料不足时必须明确说明"现有资料无法确认，需要现场核实"（规程第 1.2 / 1.3 条），不得推测。
  4. 只读访问业务数据，任何路径都不得写库。
  5. 当前交付形态为单机单进程，不含鉴权、并发治理与持久化存储。

1.3 质量目标与取舍优先级

优先级质量属性设计对应
1正确性 / 不编造规程算术下沉为代码、证据由代码汇总、接地校验、断言化回归
2安全性四层只读守卫、参数白名单、上下文预算、施压用例常态化
3可复核性span 级链路追踪、证据可展开到原文、口径显性标注
4可维护性判定逻辑单点实现（页面与命令行共用）、工具计量注册表 + 测试守卫
5延迟让等待可见优先于压低总耗时；可控项（工具调用次数、答案长度）单独治理

4.3 异常与降级路径

情形处理留痕
SQL 被守卫拒绝 / 执行报错错误文本回灌模型，允许重写一次TOOL span 记 DEGRADED
上下文预算超额拒绝该次调用并回灌可执行的修正建议；该调用不计费GUARD span 记 DEGRADED

问题不落在四类资料内合规出口：结论段首句写明"该问题超出随题资料范围"即放行，不逼模型查无关资料凑数正常收口

五、关键机制

5.1 工具契约

四个工具，六条规则收在 check_rule 一个工具里用 enum 区分而不是拆成六个： 工具数量超过五六个后模型选错工具的概率明显上升，收成一个之后模型的决策从"在九个工具里挑" 降级为"挑对一个工具 + 挑对一个枚举值"，且新增规则不必改动工具清单。

工具入参返回span 类型
query_dbsql（单条 SELECT）列名、行、行数、错误文本TOOL
search_docsquery、doc（枚举）、top_k（默认 4）标题 + 160 字摘要；命中无悬念时直接带回 top-1 全文RAG
get_doc_sectiondoc、section_id（如 24002 / 4.1）该节全文RAG
check_rulerule（六选一）、turbine_id / fault_code / work_order_id / 窗口起止等参数白名单判定结论、逐项事实、引用条款号与 clause_texts 内联原文RULE

5.2 只读访问的四层守卫

层手段是否安全边界
L1 连接层URI mode=ro，SQLite 引擎层面拒绝写是
L2 会话层PRAGMA query_only = ON是
L3 授权层set_authorizer 白名单：只放行 SELECT / READ / FUNCTION；表级白名单 alarm_records、maintenance_records是
L4 语句层单语句、SELECT/WITH 开头、关键字黑名单、自动补 LIMIT 200、2 秒超时否（主要职责是给出模型看得懂的错误信息以便重写）

L4 排在最后是刻意的：正则是最弱的一环。回归中有一条绕过 L4 直连数据库的用例，验证 L1~L3 仍拒绝写入。

5.3 上下文预算：把红线做成运行时机制

档位阈值语料基数作用
数据行合计50%62 行 → 31 行防"把库搬进上下文"
文档字符合计70%6538 字符 → 4576 字符防跨文档累计搬运
单份文档60%按各文档全文单独计实际承重层：合计档拦不住"把一份文档搬空"（手册全文仅占合计语料 57%）
  • 每次工具调用前预检，超额即拒绝并回灌修正建议；被拒绝的调用不计费，反复尝试也无法绕过。
  • 累计计量，分多次少量取回同样会被拦住；check_rule 内联的条款原文一并计入。
  • 单份文档档只判覆盖，不判取回——该口径是实跑标定出来的：按取回口径两档都判时，26 条用例误伤 3 次，全部出在取回侧（通则调用把条款原文内联两次即顶到上限，而去重后其实只读了规程的三分之一）。重复取回由合计取回档兜底。
  • 用量随回答返回（meta.budget），可在界面查看与事后审计。
三处已知缺口，不应说成"全都管住了"： ① 预算只计量语料内容，不计量提示词总长（SQL 文本、工具参数、历史消息不在其中，由步数上限间接兜底）； ② 计量规则以注册表 METERS 维护，未登记的工具按结果字符数保守计入文档预算，并有测试守卫断言注册表全覆盖； ③ 规则引擎自查的行不计入数据行预算——口径是刻意的（预算计的是进入上下文的语料，进去的是算完的结论）， 代价是水位读数低于系统实际触达的语料量。

5.4 规程判定下沉为代码

规则依据条款输出
repeat_fault3.1任意连续 24 小时滑动窗口的最大次数、各次时间、窗口外被排除的记录
priority_required2.1~2.4应有优先级与现有工单是否需要升级
work_order_assessment2.4 / 7.1~7.2优先级、状态、处理记录、观察时间、备件五项逐项核对
remote_reset_ban4.1~4.2五款逐款核对结果
close_compliance6.1~6.5七项必备记录、EEPROM 附加项、120 分钟观察门限
replace_precondition5.1~5.2 / 7.3九项前置条件逐项标注满足 / 不满足 / 无法确认

次数、时长、阈值比较一律由代码计算，模型只负责引用结论。理由是这类算术模型算错时错得很自然： 以重复故障为例，第 3.1 条要求的是任意连续 24 小时，若按自然日分组，某台风机的五条告警会被算成 3 次加 1 次，结论碰巧仍成立但过程是错的，换一组数据就会翻车。

两处判定口径需特别说明：

  • 第 4.1 条第 4 款"无法确认设备安全状态"不自动判成立。数据库永远不记录设备安全状态， 判其成立则该款恒为真、失去判别力；判其不成立又违背第 1.3 条保守处置原则。 因此标注为"资料无法确认"并援引第 1.3 条，保持为待现场核实项。
  • 第 6.1 条七项记录为关键词启发式。resolution_note 是自由文本，无法精确判定， 因此一并返回备注原文，并在无法确认项中写明应由人工对照复核。

5.5 检索设计

要素设计理由
切块单位手册按 ### 故障码（9 块）、规程按「第 x.x 条」（25 块）召回结果天然就是"章节或条款"，可直接作为依据展示，无需二次定位
打分自实现 BM25 + 精确命中加权（故障码 +5、条款号 +5、标题全词 +3）+ 停用词表语料仅约 16 KB，向量库在此规模属过度设计且不可解释
码→节映射库内 24002 ↔ 手册标题 24002_SC_变流器心跳不建映射则模型拿库里查到的裸码去检索会静默落空——不报错、答案照出，最难发现
两段取回search_docs 只回摘要，get_doc_section 才回全文进入上下文的永远只有模型明确点名的那一节
内联 top-1命中无悬念（精确锚点命中或 top1 ≥ 2.5 × top2）时直接带回 top-1 全文，且只带一节省一次往返（一轮 3~5 秒）；带四节全文就不是检索而是搬运，正踩红线
召回回归37 条检索探针（retrieval_probes.yaml），由单元测试消费，不走模型漏召回是静默的：链路显示"命中 4 节"是绿的，而该命中的那节排在第 9——单条查询自身分不出漏没漏

5.6 证据链与接地校验

  • evidence 与 sources 不由模型自报，而是从真实发生过的工具调用中汇总：执行过哪条 SQL、取回过哪一节、调用过哪条规则。这样"依据展示"在结构上就不可能被编造。
  • 模型只负责结论文本与"无法确认"清单，按固定三段标题输出，由代码确定性解析；解析失败降级为原文显示并标注。
  • "依据"段由代码从证据渲染而非模型复述：既省生成时间（约 300 字符 ≈ 3~4 秒），又少一次转述漂移的机会。踩过的坑：删掉依据段后模型输出反而变长——提示词里唯一的长度纪律恰好写在该段说明里，删段时连带删掉了它，必须为结论段补回独立的长度约束。
  • grounding.py 校验答案中的数值与条款号是否在证据中出现过，分 off / shadow / enforce 三档，默认 shadow 只标注。会误伤正确结果的判定层必须先影子跑标定再切拦截。

5.7 可观测：span 模型与两档质量口径

span覆盖状态
MODEL每次模型调用，带 Token 与折算成本OK / DEGRADED（按预期收紧）/ ERROR
TOOLquery_db
RAGsearch_docs / get_doc_section
RULEcheck_rule
GUARD预算拦截、未取证打回、接地校验

护栏单独成类且可标 DEGRADED 是刻意的：预算拦截与未取证打回都不是错误， 而是系统按预期收紧了行为——这类事件若不留痕，事后无法判断链路为何变短。

质量指标分两档且分母互不相交：离线评测（固定用例 + 断言，判得出对错）与线上质量 （真实流量，没有标准答案，一个"准确率"都不出现）。后台执行的回归链路标 source=eval， 一条都不进线上质量；两档也不合成"综合质量分"——合成后没人说得清分数变动是用例挂了还是线上降级了。

5.8 离线回放

eval/run.py 的产物同时充当回放素材。匹配采用问句覆盖度 + 标识符硬门： 问句中出现的风机编号、故障代码、工单编号必须在被匹配用例中同样出现，否则直接拒绝。 仅用文本相似度会出错——"T20 的型号是什么？"与"T01 的风机型号是什么？"覆盖度达 0.86， 而 T20 并不在库中（库内为 T01~T09）。

八、非功能设计

8.1 延迟

逐次调用埋点的结论与直觉相反：

成本项实测结论
网络往返与最小调用开销0.84s改为按配置缓存客户端，避免每题重做 TCP + TLS 握手
系统提示词预填充（5792 字符）≈ 0s精简提示词无收益，却会损失 SQL 生成质量与判定纪律——这条常见优化在此被证伪
工具执行（SQL、BM25、规则）0.92s，占 5%检索不是瓶颈（SQL 3.3ms、BM25 热态 0.2ms）
生成最终答案13.08s，占 69%耗时 ≈ 串行模型轮数 × 每轮输出长度，治理方向由此确定

据此的三项改造：依据段改代码渲染、search_docs 内联 top-1 省一次往返、连接复用与启动预热。 26 条用例实测 P50 17.6s → 13.2s（−25%）、合计 538.5s → 377.0s（−30%）、一步题 P50 11.2s → 6.6s。 但端到端耗时在不同批次间波动很大（同一用例曾录得 12.5s 与 42.1s，工具调用次数仅差 1）， 因此不宣称可复现的总耗时收益；可复现的是答案长度下降与首字时间的机制性改变。

混算的分位数描述的是题目难度分布而不是系统性能，因此指标按工具调用次数分桶给出： 1 步 / 2-3 步 / 4 步以上各自的 P50 与 P95。

8.2 成本

Token 与成本来自流式返回的 usage；缓存命中的输入按官方缓存单价单独折算 （按标准输入价计算会明显高估）。单价集中在 tools/pricing.py 并注明核对日期，可用环境变量覆盖—— 写死一个记忆中的数字，会让整张成本表在毫无察觉的情况下全错。

8.3 可靠性与安全

  • 失败也留痕：模型超时或网关报错时留下 ERROR 的 MODEL span，整条链路以 FAILED 进留存——只统计跑通的链路会让成功率恒为 100%，等于装饰。
  • 威胁模型：不是注入，是施压。资料是静态可信文件，唯一外部输入是提问者自己的问题，而提问者即操作者，不存在需要跨越的权限边界；SQL 注入这条真实路径由四层守卫与规则参数白名单拦截。真正的风险是用户要求系统放弃保守判定，为此单列 9 条施压用例（含索要提示词、角色扮演、伪造工具结果、伪 system 覆盖四种注入形态）持续检验。
  • 业务数据全程只读；系统不提供任何写入路径，用户要求"改数据"时明确拒绝并说明库中值未变化。

九、架构决策记录（ADR）

ADR-01　不引入 Agent 框架

决策
采用原生 Function Calling 循环（核心约 150 行）。
备选
LangGraph / LangChain。
理由
本场景为四个工具、至多六步、单轮问答、无需断点续跑；框架的调度抽象与依赖成本高于收益，且会削弱执行轨迹的可控性，而轨迹展示是硬性要求。
代价 / 触发再评估
扩展到多轮会话、断点续跑或人工介入审批时，引入 checkpoint 机制是合理演进。

ADR-02　检索单位 = 一个标题小节

决策
按故障码小节与「第 x.x 条」切块，检索即返回可直接展示的依据单位。
代价
块粒度受文档标题结构约束；换一套排版需调整切块规则。

ADR-03　BM25 + 精确加权，不引入向量库

理由
语料约 16 KB，精确匹配加权已能把目标章节稳定顶到首位，且可解释。
代价
不具备语义泛化：问法与文档用词完全不同时（只说"心跳丢了"不提故障码）召回质量下降。演进方向为 RRF 混合。

ADR-04　规程判定下沉为代码，模型只引用结论

理由
滑动窗口、阈值比较这类算术，模型算错时错得很自然、不易察觉。
代价
规则与本规程绑定（条款号、阈值、必备记录项硬编码），换制度需改代码；演进方向为规则配置化。

ADR-05　六条规则收进一个工具

理由
工具数量超过五六个后模型选错工具概率明显上升；收成一个后新增规则不必改动工具清单。
代价
单个工具的参数面变宽，需以参数白名单与枚举说明约束。

ADR-06　代码侧强制首步检索，而非依赖厂商参数

背景
最初用 tool_choice="required"，但 qwen3 系列在思考模式下不支持该参数。
决策
改为代码侧拦截：未调工具即打回要求先检索，二次仍不调则拒答；另设范围外合规出口，避免逼模型查无关资料凑数。

ADR-07　证据由代码汇总，不经模型转述

理由
依据展示在结构上就不可能被编造，用户看到的 SQL 与章节原文一定是系统实际用过的。

ADR-08　接地校验默认 shadow

理由
会误伤正确结果的判定层必须先积累真实误判样本；本机构造的样例想不出真实误判形状，离线重放也标不出来。
触发切换
误判样本沉淀为回归用例且连续两轮零误伤后切 enforce。

ADR-09　单份文档预算档只判覆盖不判取回

背景
两档都判时实跑误伤 3 次，全部出在取回侧。
理由
红线问的是"整份文档是不是被搬进去了"，那本来就是去重口径的问题；重复取回由合计取回档兜。
教训
会误伤的新判据，光靠产物离线复算标不出真实的误伤形状，必须真跑一轮。

ADR-10　观测不落库、诊断与度量分页

决策
链路进程内留存 50 条；链路页不出聚合指标，聚合口径统一归质量中心，且离线与线上两档分母互不相交。
理由
引入持久化会带来新的状态与故障模式；同一指标在两处按不同口径并存，会让人在两个正确的数字之间怀疑系统坏了。
代价
重启后线上样本清零，页面显式写明样本量与时间窗。
