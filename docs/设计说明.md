# 海上风电机组维检 Agent · 设计说明

- 版本：V1.0
- 日期：2026-09-16

本文记录方案的结构、关键技术选择及其理由，以及当前实现的边界。运行方式与评测结果见 `../README.md`。

---

## 一、问题分析

题目提供四类资料，分属两种介质：

| 资料 | 介质 | 特点 |
| --- | --- | --- |
| 运行告警记录 | SQLite 表 `alarm_records` | 结构化，需要按风机、故障码、时间区间筛选与计数 |
| 维检工单记录 | SQLite 表 `maintenance_records` | 结构化，含自由文本字段 `resolution_note` |
| 故障处理手册 | Markdown | 按故障代码分节，每节内有固定四个子标题 |
| 检修作业与安全管理规程 | Markdown | 按「第 x.x 条」分条，共 25 条 |

问题的难度分层来自**需要几类资料以及它们之间的依赖关系**：

- 单源问题：只查一张表或只定位一个章节；
- 多源问题：先从库中取得事实（故障码、发生次数、工单字段），再用这些事实去文档中确定规则，
  最后融合成判断。第二次检索依赖第一次的结果，因此不能一次性并行取回。

此外，资料本身有明确的边界。规程第 1.2 条列举了数据库不记录的内容——母线电压、
退出远程控制、挂牌上锁、验电、人员资质、海况天气。涉及这些的问题**不存在正确答案**，
只存在正确的回答方式：明确说明无法确认。因此「无法确认」必须是系统的一等输出，
而不是答不出来时的兜底话术。

## 二、总体结构

```
用户提问
  ↓
Function Calling 循环（≤6 步）
  ├─ query_db          只读守卫下执行 SELECT
  ├─ search_docs       标题级章节召回，只返回摘要
  ├─ get_doc_section   取回整节全文
  └─ check_rule        六条确定性规程判定
  ↓
三段解析：结论 / 依据 / 现有资料无法确认
  ↓
证据与数据源由代码从真实工具调用汇总
  ↓
接地校验（默认只标注）→ 返回
```

## 三、关键设计与取舍

### 3.1 不引入 Agent 框架

本题的规模是四个工具、至多六步、单轮问答、无需持久化 checkpoint。评估过 LangGraph /
LangChain，结论是框架引入的调度抽象与依赖成本高于收益，并且会削弱执行轨迹的可控性——
而轨迹展示是题面的明确要求。因此采用原生 Function Calling 循环，核心约 150 行。

若扩展到多轮会话、需要断点续跑或人工介入审批，再引入 LangGraph 的 checkpoint 机制
是合理的演进方向。

### 3.2 检索单位 = 一个标题小节

故障手册按 `###` 故障码切块（9 块），规程按 `### 第 x.x 条` 切块（25 块）。这样切的好处是
**召回结果天然就是「章节或条款」**，可以直接作为依据展示给用户，不需要再做二次定位。

打分为 BM25 加精确命中加权（故障码 +5、条款号 +5、标题全词 +3）。BM25 为自行实现，
未引入检索库。语料仅约 16 KB，向量库在此规模下属于过度设计，且不可解释；
精确匹配加权已能把目标章节稳定顶到首位。代价是不具备语义泛化，见第五节。

**向量召回与 BM25 混合实测过一轮，没有落地：融合后的整体召回没有跑赢纯词表路径。**
这不是"没试就否掉"，而是试完之后的结论——所以第六节的演进方向里不再把它排在前面。
需要说明的是，当次融合 / 词表的逐条对比明细未留存在仓库内，可复现的只有
`tests/test_retriever_recall.py` 的探针集分数；后续若重做这个对比，应当以该探针集为准并把
明细落盘，否则下一个人还要再踩一遍同样的坑。

语义缺口的位置是明确的，也不靠猜：37 条检索探针分五组，当前 top-4 召回整体 81%
（加停用词表前 76%），其中**只有 C 组塌陷到 42%**（5/12），A / B / D / E 四组均为 100%。
C 组恰恰是"口语化、与文档用词零重合"的那一类——「同一台机器一天之内连着报了好几次
一模一样的错」要命中「第 3.1 条 重复故障」，「能不能坐在后台直接把这个报警清掉」要命中
「第 4.1 条 远程复位」。缺口集中在这里，意味着更值得做的是贴题的同义词与别名映射，
而不是把 16 KB 语料塞进向量空间。

**必须处理的一处口径差异**：数据库中 `fault_code` 是裸码 `24002`，而手册标题是
`24002_SC_变流器心跳`。不建立 `code → section` 映射的话，agent 拿库里查到的码去检索文档
会静默落空——不报错、答案照出，是最难发现的一类缺陷。

### 3.3 检索与取全文拆成两个工具

`search_docs` 只返回标题与摘要，`get_doc_section` 才返回全文。一步到位地返回全文，
多召回几个块就会把上下文撑爆，而题面明确要求不得将整份文档放入模型上下文。
拆开之后，进入上下文的永远只有模型明确指定的那一节。

### 3.4 规程判定下沉为代码

规程中的判定全部可计算：24 小时滑动窗口计数、120 分钟观察阈值、关闭必备的七项记录、
更换前置的九项条件。这些交由 `rules.py` 计算，模型只负责引用结论。

理由是这类算术模型算错时错得很自然、不易察觉。以重复故障为例，第 3.1 条要求的是
**任意连续 24 小时**，若按自然日分组，T03 的五条告警会被算成 3 次加 1 次，
结论碰巧仍然成立，但过程是错的，换一组数据就会翻车。

六条规则收在一个 `check_rule` 工具里用 `rule` 枚举区分，而不是拆成六个工具。
工具数量超过五六个后，模型选错工具的概率上升明显；收成一个之后，模型的决策从
「在九个工具里挑」降级为「挑对一个工具加挑对一个枚举值」，并且新增规则不必改动工具清单。

两处需要说明的判定口径：

- **第 4.1 条第 4 款「无法确认设备安全状态」不自动判成立。** 数据库永远不记录设备安全状态，
  若判其成立，该款将恒为真、失去判别力；若判其不成立，又违背第 1.3 条保守处置原则。
  因此标注为「资料无法确认」并援引第 1.3 条，使其保持为一个待现场核实项。
- **第 6.1 条七项记录的判定是关键词启发式。** `resolution_note` 是自由文本，无法做到精确判定，
  因此结果中一并返回备注原文，并在无法确认项中写明应由人工对照复核，不将其呈现为精确结论。

### 3.5 只读访问的四层防护

| 层 | 手段 |
| --- | --- |
| L1 连接层 | URI `mode=ro`，SQLite 引擎层面拒绝写 |
| L2 会话层 | `PRAGMA query_only = ON` |
| L3 授权层 | `set_authorizer` 白名单，只放行 SELECT / READ / FUNCTION |
| L4 语句层 | 单语句、SELECT/WITH 开头、关键字黑名单、自动补 LIMIT、2 秒超时 |

语句层正则排在最后，是因为它是最弱的一环：它的主要职责是产生一句模型看得懂的错误信息
以便重写重试，而不是充当安全边界。真正的边界在 L1~L3。测试中有一条绕过 L4 直连数据库，
验证引擎层仍然拒绝写入。

SQL 执行错误不向上抛出，而是以错误文本回灌给模型，允许重写一次。

### 3.6 首步强制检索

题面要求必须通过检索取得依据，不得将整个数据库或文档放入上下文。模型有时会认为问题简单，
一个工具都不调用就直接作答，这就越过了这一约束。

最初使用 `tool_choice="required"` 强制首步调用工具，但 qwen3 系列在思考模式下不支持该参数。
改为代码侧强制：一次工具都未调用就试图作答时打回要求先检索，仍不调用则直接拒答，
而不是放行一个没有依据的回答。这样不依赖任何厂商的参数支持。

### 3.7 证据由代码汇总，不经模型转述

回答契约中的 `evidence` 与 `sources` 不是让模型自己报的，而是从真实发生过的工具调用中汇总：
执行过哪条 SQL、取回过哪一节、调用过哪条规则。这样「依据展示」在结构上就不可能被编造，
用户看到的 SQL 与章节原文一定是系统实际用过的。

模型只负责产出结论文本与「无法确认」清单，按固定三段标题输出，由代码确定性解析。
解析失败时降级为原文显示，并在界面标注已降级，不伪装成解析成功。

### 3.8 接地校验默认不拦截

`grounding.py` 校验回答中出现的数值与条款号是否在证据中出现过，分 `off` / `shadow` / `enforce` 三档，
默认 `shadow`——只标注，不改动回答。

这类判定层会误伤：模型正确引用了规程中的数字，但该段原文本轮未被取回，就会被标为缺证据。
需要先积累真实误判样本再切 `enforce`，否则会连正确答案一起拦掉。

### 3.9 界面按信息结构组织

界面分为能力说明、提问、执行时间线、回答、无法确认提示、数据源、结论依据、原始依据八块。
其中两处是刻意安排：

- **能力说明区同时写明「无法回答什么」**，把现场安全条件、责任归属等明确列为系统边界，
  使用户在提问前就知道哪些问题不会得到肯定答复。
- **回答与依据在视觉上分离**，依据区默认折叠、按需展开原始 SQL、命中行与章节全文，
  既不干扰阅读，又保证结论可回溯。

失败路径分四种给出不同文案：证据不足、检索为空、SQL 出错、模型超时。

### 3.10 离线回放

`eval/run.py` 的产物同时充当回放素材，`REPLAY_MODE=true` 时无外网亦可走完整界面流程，
界面明确标注当前为回放模式及匹配到的用例。

匹配采用「问句覆盖度加标识符硬门」：问句中出现的风机编号、故障代码、工单编号必须在
被匹配用例中同样出现，否则直接拒绝。仅用文本相似度会出错——「T20 的型号是什么？」
与「T01 的风机型号是什么？」覆盖度达 0.86，而 T20 并不在库中。

## 四、回归设计

11 条用例覆盖单源与多源、正向与反向场景，其中三条是反向陷阱：

- T03 / 24002 有一条记录相隔超过 24 小时，不得计入同一窗口；
- T07 / 24012 窗口内仅 2 次，**未**达到重复故障标准；且数据库中**没有**对应工单，
  必须如实回答不存在，不得编造；
- T09 / WO-260708 状态为 `COMPLETED`，但备注与观察时间均不满足关闭要求。

断言写法经过五次修正后定下约定：`must_include` 仅用于模型必然逐字复现的 token
（工单号、枚举值、时间戳）；一切自然语言判定改用正则，把同义表述写入选择分支；
断言只作用于模型自己产出的文字，不作用于证据原文——证据中是手册与规程原文，
含大量数字与术语，对其做否定断言必然误判。

### 3.11 让等待过程可见，而非追求耗时数字

单次模型调用的延迟受网络与服务端波动支配：同一用例在不同批次测量中可相差数倍
（Q3 曾录得 12.5 秒与 42.1 秒，而两次的工具调用次数仅差 1）。在这种方差下，
本地测得的耗时既无法优化到位，也无法预测部署环境的实际表现。

因此接口改为 SSE 流式返回，每完成一次工具调用即推送事件，界面实时追加轨迹并显示已用时。
工具调用次数这一可控指标则通过条款原文内联从 57 次降至 39 次（−32%）。

### 3.12 上下文预算：把题面红线做成机制

题面要求不得将整个数据库或文档放入模型上下文。事后统计 21 条链路，单次会话最多只用到
全库约 21% 的行、全部文档块的 6%——但那是行为结果，不是保证：架构上并不存在阻止
`SELECT * FROM alarm_records` 的机制（全表 47 行，低于自动追加的 LIMIT 200）。

因此增加运行时预算：每次工具调用前预检，累计数据行超过语料 50%、或文档字符超过语料 70% 即拒绝，
并把可执行的修正建议回灌给模型；累计计量使分次少量取回同样被拦住；
`check_rule` 内联的条款原文一并计入。用量随回答返回，可展示与审计。

**合计口径拦不住「把一份文档搬空」**（2026-09-18 补）。上面那个 70% 的分母是两份文档
合计 6538 字符，而故障处理手册全文只有 3845——整本手册逐节取进上下文，合计口径也只有
57%，低于阈值，护栏一声不吭。而红线写的是「整个数据库或**文档**」，合计档回答不了
「某一份是不是被搬空了」这个问题。

因此每份文档再各设一档，超过该文档全文的 60% 即拒绝。阈值是标定过的：拿 27 条跑测产物
按去重口径复算每条链路的单文档水位，峰值 34.9%（P8「远程复位禁止情形」，规程侧
940 / 2693 字符），定在 60% 留 1.7 倍余量。

**这一档只判覆盖，不判取回**——而这一条是跑测跑出来的，不是设计出来的。先前照着合计档
的样子两档都判，26 条用例实跑误伤 3 次（X2 两次、P8 一次），**全部出在取回侧**：
`check_rule` 的通则调用会把该规则覆盖的条款原文一并内联，一个合规问题连调两次，
累计取回就顶到 1615 字符的上限，而去重后其实只读了规程的三分之一。

离线标定之所以没拦住它，是因为复算的是覆盖口径——取回口径要按"每一次调用各算一份"
重放，产物里存的是汇总后的证据，重放不出来。教训是具体的：**会误伤的新判据，光靠
产物离线复算标不出真实的误伤形状，必须真跑一轮。** 口径本身也站得住：红线问的是
"整份文档是不是被搬进去了"，那本来就是去重口径的问题；重复取回由合计取回档去兜。

实际承重的只有这一层。另外三层是设计压力而非保证：

| 层 | 作用 | 是否硬保证 |
| --- | --- | --- |
| 系统提示词注入 schema 而非数据 | 模型能写 SQL，但看不到任何一条记录 | 是（结构上不含数据） |
| `search_docs` 只返回摘要（每节 160 字符、至多 4 节） | 检索不带全文，要全文须显式点名章节 | 否（不阻止反复取回） |
| `query_db` 自动补 `LIMIT 200` | 防超大结果集 | 本题不承重：全库仅 62 行，该限制永不触发 |
| **上下文预算** | 预检、超限拒绝、累计计费 | **是** |

三处已知缺口，不应说成"全都管住了"：

1. 预算只计量语料内容，不计量提示词总长。SQL 文本、工具参数与累积的历史消息不在其中，
   目前由 `AGENT_MAX_STEPS=6` 间接兜底。
2. 计量规则以注册表 `METERS` 维护。未登记的工具会按其结果字符数保守计入文档预算
   （宁可高估被拦，不可静默漏计），并有测试守卫断言 `TOOL_REGISTRY` 中每个工具
   都已登记——新增工具却忘记计量是最难发现的一类缺陷。
3. **规则引擎自己查库取回的行不计入数据行预算**，只有内联的条款原文计入文档预算。
   口径是刻意的：预算计量的是「进入模型上下文的语料」，而这些原始行并不进上下文——
   进去的是规则算完的结论与派生事实。代价是水位读数会低于系统实际触达的语料量
   （例如一次 `repeat_fault` 判定读了 5 行，而 `meta.budget.db_rows` 仍为 0）。
   这层的承重前提是 `check_rule` 的返回结构由代码固定构造、不回填原始行；
   若将来有规则把行放进 `facts`，这些行会绕过计量进入上下文。

### 3.13 威胁模型：不是注入，是施压

经典 prompt 注入的前提是不可信内容以高于其作者的权限进入模型。本题中资料是随题提供的
静态可信文件，唯一的外部输入是提问者自己的问题，而提问者即操作者——不存在需要跨越的
权限边界。SQL 注入这条真实路径由四层只读守卫与规则引擎的参数白名单拦截。

实际风险在另一处：用户以各种方式要求系统放弃「现有资料无法确认」的保守判定，
而那恰是本题的核心考点。为此单列 `eval/pressure.yaml` 五条用例持续检验。

### 3.14 耗时构成：瓶颈在生成，不在检索

对一条四步问答做逐次调用埋点，结果与直觉相反：

| 成本项 | 实测 |
| --- | --- |
| 网络往返与最小调用开销 | 0.84 秒 |
| 系统提示词预填充（5792 字符） | 约 0 秒 |
| 工具执行（SQL、BM25、规则判定）合计 | 0.92 秒，占 5% |
| 生成最终答案（1402 字符，约 94 字符/秒） | 13.08 秒，占 69% |

结论有三点：

1. **精简提示词无收益。** 预填充成本实测接近于零，缩短系统提示词一秒也省不下来，
   却会损失 SQL 生成质量与判定纪律。这条常见优化在此被证伪。
2. **检索不是瓶颈。** 数据库查询、BM25 召回与规则计算合计仅占 5%。
3. **答案长度直接决定耗时。** 因此做两件事：一是收紧「依据」段的输出要求
   （界面已单独展示原始 SQL、命中行与条款全文，答案中不再复述），
   答案长度由约 1402 字符降至约 1162 字符；二是把最终答案改为逐字流式返回。

流式改造后，界面的时间线为：约 4.5 秒出现查询轨迹，约 11 秒答案开始逐字浮现，
约 20 秒完成。改造前则是全程无输出直到结束。

**第二轮（2026-09-18）**。26 条用例混算的 P95 是 38.4 秒，但混算的分位数描述的是
**题目难度分布**而不是系统性能：按工具调用次数分桶后，一步题 P50 11.2 秒、四步以上
P50 31.8 秒。耗时 ≈ 串行模型轮数 × 每轮输出长度，本地工具（SQL 3.3 毫秒、BM25 热态
0.2 毫秒）连噪声都算不上。据此做了三件事：

1. **「依据」段改由代码从证据渲染。** 这一段原先由模型复述约 300 字符，按实测
   84~110 字符/秒就是 3~4 秒。而它复述的恰恰是 `evidence` 里已有的东西——规则判定的
   `verdict` 是规则引擎算出来的原话，命中行数是执行结果。拿 27 条产物离线复算，
   换成代码渲染后 27/27 条断言结果不变。既省生成时间，又少一次转述漂移的机会。

   这里有个反直觉的坑：**删掉「依据」段之后，模型的输出反而变长了**。第一轮实跑
   26 条，结论段中位数从 270 字符涨到 571。原因是提示词里唯一的长度纪律
   （「不超过 5 行、每行不超过 60 字」「不要展开论证」）恰好写在依据段的说明里，
   整段删掉时连带删掉了它，而结论段从来没有自己的长度约束——先前是靠依据段间接兜着的。
   补回结论段的长度纪律后才拿到预期收益。
2. **`search_docs` 在命中无悬念时直接带回 top-1 全文**，省掉一次 `get_doc_section`
   往返（一轮 3~5 秒）。判据是精确锚点（问句里的故障码或条款号命中该节）或得分
   显著领先（top1 ≥ 2.5 × top2）；召回自身报 low_confidence 时一律不带。
   **只带 top-1**：手册一共 9 节，top-4 里最大的四节合起来就是整本的 59%，
   四节全带全文就不是检索而是搬运，正踩红线。带一节则与 `get_doc_section` 注入的是
   同一段原文，合并后上下文内容不增反减（少一份摘要）。
3. **连接复用与启动预热。** 原先每轮问答新建一个 OpenAI 客户端，等于每题重做一次
   TCP + TLS 握手；本机经 VPN 出网实测 RTT 386 毫秒，建连一项就吃掉 0.8~1.2 秒。
   改为按配置缓存客户端。另外检索索引与 jieba 词典是懒加载的（首次约 1.2~2.4 秒），
   原先落在进程起来后的第一个提问上，现在服务端启动与命令行跑测器都先预热——
   后者尤其要紧：那批数字正是用来判断优化有没有效果的，不能掺进一个冷启动。

顺带纠了一处口径漂移：离线档与线上档各写了一份 P95，离线档用的 `round(0.95*(n-1))`
正是线上档注释里已经判为偏乐观的写法（n=39 时把最慢的两条整个排除）。两处统一到
`agent/tracing.py` 的同一份实现。

26 条用例实测结果（2026-09-18，26/26 断言通过）：

| | 改造前 | 改造后 |
| --- | --- | --- |
| P50 | 17.6s | **13.2s**（-25%） |
| P95 | 38.4s | **34.3s**（-11%） |
| 26 条合计 | 538.5s | **377.0s**（-30%） |
| 一步题 P50 | 11.2s | **6.6s** |

26 条里 22 条变快。剩下 4 条中最大的一个离群点（X4，9.1s → 35.6s）经逐段核对是服务端
侧的延迟尖峰：答案长度前后一致（297 / 294 字符）、输出 token 反而更少，但其中一次
决策调用花了 28.9 秒只吐出 116 token，约 4 token/秒，而正常水平是 30~40。
单次调用的延迟波动压不下去，这也正是流式返回要解决的问题——它让等待可见，
而不是让等待变短。

实现上有一处必须处理：**决策轮也会输出自然语言**。模型在发起工具调用的同时，
往往会顺带写一句「我需要先查询告警记录」。若把所有内容增量都当作答案推给界面，
就会出现「冒出几个字又被下一次工具调用冲掉」的反复闪烁。
因此以提示词强制的三段标题为界——见到 `## 结论` 才认定进入最终答案，此前的内容一律不推送；
并保留两条兜底：同一轮里既出现标题又发起了工具调用时发 `answer_reset` 撤销已渲染内容，
模型完全未按格式输出时在该轮结束一次性补发。

需要说明的是，端到端耗时在不同批次间波动很大（同一用例曾录得 12.5 秒与 42.1 秒，
而工具调用次数仅差 1），因此上述改造**不宣称**带来可复现的总耗时收益；
可复现的是答案长度的下降与首字时间的机制性改变。

### 3.15 Agent 质量中心：两种口径分开摆，不合成一个分数

`GET /admin` 的第一个视图，内部分两档：

- **离线评测** —— 样本是 `eval/` 下的固定用例，有断言，判得出对错；展示三套用例的通过
  情况、耗时、工具调用次数与上下文用量，可逐条展开完整执行链路。数据源是 `eval/run.py`
  已经落盘的 JSON 产物，页面只做渲染。
- **线上质量** —— 样本是用户在问答页真实提出的问题，**没有标准答案**；因此这一档一个
  「准确率」都不出现，只报系统自己留下的痕迹：有没有正常收口、有没有因未取到证据而拒答、
  有没有把「现有资料无法确认」标出来、上下文压到了哪、一次问答花了多少。

**两档的分母必须互不相交。** 后台点「运行全部」跑出来的链路标为 `source=eval`，一条都不
计入线上质量。回归用例是挑好的题目，混进线上指标会把成功率抬着走，而线上质量要回答的
恰恰是「真实用户问出来的东西，系统接得住吗」——用有标准答案的口径去解释没有标准答案的
数据，得到的数字看着漂亮，指示不了任何东西。

也不把两档合成一个「综合质量分」：加权一合，分数变动时没人说得清是用例挂了还是线上降级了，
而这两件事的处置方式完全不同。

**仍然不做成管理后台**：线上那一档取的是进程内最近 50 条链路，不加持久化、不引入数据库，
重启即清空并在页面上写明样本量与时间窗。题面明确「不要求实现生产级系统」，并提醒
「不建议为了覆盖全部问题而堆叠大量未经验证的功能」——真正需要的是把已经产生的痕迹**读出来**，
而不是再造一套存储。

判定逻辑抽到 `eval/verdict.py` 由跑测器与页面共用。两处各写一套必然随时间漂移，
而「同一条用例在命令行与页面上给出不同结论」是最难排查的一类缺陷。

### 3.16 链路追踪：为了复核，不是为了监控

题面要求展示「简要查询过程」，但要判断 agent 的决策是否**合理**，摘要不够——
需要看到每一段的输入、输出、耗时与状态。因此把一次问答拆成 span，按它与模型的关系分五类：
`MODEL` / `TOOL` / `RAG` / `RULE` / `GUARD`，状态分 `OK / DEGRADED / ERROR`。

护栏单独成类且可标 `DEGRADED`，是刻意的：上下文预算拦截、未取证打回都不是错误，
而是系统按预期收紧了行为，这类事件若不留痕，事后无法判断链路为何变短。

四处取舍：

1. **独立成页，不混进问答页。** 链路明细是运维视角，放在回答下方会淹没结论与依据，
   而后者才是用户要看的。问答页保持干净，三个地址在启动时一并打印，直接访问即可。
   路由单独放在 `admin.py`（职责分离），但运行上是同一个进程同一个端口——
   链路留存为内存态，拆进程后后台就读不到问答侧的记录。线上问答与回归跑测的链路
   都在这一页，各自带来源标并可单独筛选：复核要看全部过程，做口径区分的是质量中心。
2. **进程内留存，不落库。** 保留最近 50 条足以横向比较链路，而引入持久化会带来
   新的状态与故障模式；重启即清空这一点在页面上写明，不假装是存储。
3. **这一页不出聚合指标。** 诊断与度量是两件事：同一个「工具调用成功率」在这里
   （最近 50 条、线上与回归混着、重启归零）与在质量中心（固定用例集 / 真实流量，两档分开）
   必然不同值，两处并存等于让人在两个正确的数字之间怀疑系统坏了。顶部只留导航信息——
   留存多少、线上与回归各多少、降级与失败各多少、可一点即筛——聚合口径统一归质量中心。
4. **计价单价必须注明来源与核对日期。** 写死一个记忆中的数字，会让整张成本表在
   毫无察觉的情况下全错。缓存命中的输入按缓存价单独折算——实测命中占比约 67%，
   按标准价计算会明显高估。

### 3.17 现场可执行的回归

质量中心的离线评测档提供直接执行入口：可跑全部用例或勾选若干条，逐条流式回报。
它与命令行跑测器共用 `eval/verdict.py` 的判定，并同样落盘产物。

这么做的理由是演示场景：当场跑一遍、看着用例逐条通过，比展示一张静态结果表有说服力得多；
而共用判定则保证页面上看到的结论与命令行一致。

### 3.18 把「无法确认」做成现场核实清单

规程第 1.2 条要求资料不足时明确回答「现有资料无法确认，需要现场核实」。
按字面实现，它是一句免责声明——系统说它不知道，对话就结束了，用户拿不到下一步。

但第 5.1 条本身就是九项具体条件，规则引擎已经逐项算出了状态。因此把这份结果
渲染成一张核实清单：哪几项系统已替用户确认、哪一项明确不满足、剩下几项需现场逐个核。
同一份数据，从「我不知道」变成「这是你要去办的几件事」——不新增任何能力，
只改变它到达用户的形式。

清单严格区分三种状态，这在电力安全场景里不是措辞问题：

| 状态 | 含义 | 示例 |
| --- | --- | --- |
| 已确认 | 资料明确支持 | 机组已停机（告警记录 STOPPED） |
| 明确不满足 | 资料明确不支持 | 备件不可用（`part_available = 0`） |
| 待现场核实 | 资料没有记录 | 挂牌上锁、验电、母线电压 |

「明确不满足」是已知的坏消息，「待现场核实」是系统的边界。混在一起报，
用户就分不清哪些已成定论、哪些还要去查。清单底部同时写明系统只读、
不能代为确认，也不据此推定其已满足（第 5.2 条）。

覆盖三类判定：更换前置条件（第 5.1 条九项）、工单关闭必备记录（第 6.1 / 6.4 条）、
工单安排五要素。只有本次实际调用过对应规则时才生成清单，不凭空构造。

## 五、当前实现的边界

1. 多步问题耗时仍偏高（最长约 40 秒）。工具调用次数已通过条款内联下降 32%，
   但总耗时受单次调用延迟支配，本地无法进一步压低。
2. 关单七项判定为关键词启发式，结果附备注原文供人工复核。
3. 接地校验处于 shadow 档，尚未启用拦截。
4. BM25 不具备语义泛化。若问法与文档用词完全不同（例如只说「心跳丢了」而不提故障码），
   召回质量会下降：检索探针 C 组（口语化、词面零重合）当前 top-4 召回 42%，
   而术语原词的 A 组为 100%。混合召回已实测过，未跑赢纯词表，见 3.2。
5. 单轮问答，不支持多轮追问与代词指代。
6. 规则引擎与本规程绑定，条款号与阈值硬编码。
7. 未做并发与鉴权设计：按单机单用户的演示场景实现，不含登录、会话与限流。
8. 未做应答缓存：演示场景下每个问题只问一次，缓存无收益；离线回放已覆盖同类需求。

## 六、演进方向

- 语义泛化：**优先做同义词与别名映射**，而不是向量召回。混合召回（RRF 融合）实测过一轮，
  整体召回未跑赢纯词表路径；缺口集中在检索探针 C 组（当前 42%），是词面映射问题
  而非向量空间问题。若要重做这个对比，须以探针集为准并落盘明细，见 3.2
- 规则配置化：条款号、阈值、必备记录项抽到配置文件，规则引擎只保留算法
- 接地校验切 enforce，并把误判样本沉淀为回归用例
- 多轮会话与上下文澄清
- 精简工具返回结构，抑制模型重复取证导致的步数膨胀
